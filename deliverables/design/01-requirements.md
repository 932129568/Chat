# GLM-Chat UI 重设计 · 需求摘要（Phase 1）

> 产出人：需求发现分析师 许明需 · 依据 `00-contract-brief.md` 与 `frontend/index.template.html` 通读结果
> 一句话需求：**在已经能跑的 Windows 桌面 AI Agent 客户端上做 UI 重设计，且前端与 Python 后端必须保持完全联通。**

## 一、五维度需求摘要

| 维度 | 结论 |
|------|------|
| 场景 | Windows 桌面客户端（pywebview 单窗口），非网页、非移动端 |
| 受众 | 重度使用 AI 编码 Agent 的开发者 / 技术用户 |
| 调性 | 专业开发工具感（高信息密度 + 清晰 + 长时间盯屏舒适） |
| 品牌 | 品牌名与功能语义保留，视觉语言重塑 |
| 规模 | 单窗口多面板；改造 = 侧栏 + 主区 + 设置面板 + 消息渲染 + 输入区 |

### 1. 场景（Surface）
- **形态**：单窗口桌面应用，`body` 为 `100vh` flex，`overflow:hidden`，固定 272px 侧栏 + 弹性主区。桌面尺寸，无移动端布局需求。
- **需承载的主要视图/面板**（改造对象，均已在现有 DOM 中存在）：
  - **会话列表**（`.session-list` + `.session-item`）：历史会话切换 / 删除，`newSession` / `switchSession` 动态渲染。
  - **消息流**（`.chat-container` + `.message`）：user / assistant 气泡、Markdown 正文、代码块、打字动画、错误态。
  - **工具调用可视化**（`.tool-call-item` / `.toolchip` / `.tool-spinner` / `.tc-head`）：Agent 执行工具（读写文件、跑命令、截屏）的实时反馈——**这是本产品的核心差异化，需重点设计**。
  - **设置面板**（`.settings-panel`，4 个 `.set-block` 网格）：API Key、模型/推理力度、省 Token 策略、生成参数、角色与联网。
  - **工作区管理**（`.ws-card` + `.eff-row`）：文件夹绑定、本会话独立、生效路径条。
  - **成本仪表盘**（`.token-stat` / `#liveTokenStat` / `.usage-info`）：实时 token、单会话预算、压缩档位——**面向"省钱"的功能叙事，应显性化**。
  - **辅助层**：流式进度条 `.stream-bar`、系统提示 `.sys-tip`、右键菜单 `.ctx-menu`、附件预览 `.attach-preview`、空状态 `.empty-state`。

### 2. 受众（Audience）
**画像：本地 AI Agent 的重度开发者用户。** 证据来自代码本身：
- 需自行配置 **API Key**（`#apiKey`）→ 用户具备技术背景，理解 API 计费。
- **工作区/文件夹绑定**（`#wsEnabled` / `#wsSel` / `#browseWs`）+ **工具权限三档**（`#toolMode`：完整 / 只读 / 纯聊天）→ 用户让 AI 直接操作本机文件与命令，对权限有明确诉求。
- **token 成本统计 + 单会话预算**（`#sessionBudget` / `#saverLevel` / `#shotQuality`）→ 用户对"花多少钱"高度敏感，追求省 Token。
- **会话历史压缩**（历史压缩档位、缓存命中提示）→ 用户进行**长会话、多轮**的连续编码协作。

**核心诉求（按优先级）**：
1. **信息密度高但清晰**——一屏内看懂模型/权限/成本/工具状态，不靠来回点击。
2. **工具调用与流式过程可见**——Agent 正在读哪个文件、跑什么命令，必须一眼可辨。
3. **成本可控可感知**——token 与花费随时可见，不惊吓。
4. **长时间使用不累眼**——低眩光、深色友好、对比度适中。
5. **操作可信**——破坏性操作（命令/写文件）有清晰的权限与状态暗示。

### 3. 调性（Tone）
三个候选视觉方向：

| 方向 | 特征 | 参照 |
|------|------|------|
| **A. 专业开发工具（推荐）** | 中性灰阶 + 单一强调色、克制的圆角与阴影、等宽字体承载工具/成本数据、深色优先 | Linear / Vercel / Warp |
| **B. 极简生产力** | 更大留白、更少边框、以排版层级代替分割线、柔和中性色 | Raycast / Notion |
| **C. 保持现状增强** | 沿用蓝紫渐变与圆角气泡，仅做精修 | 现状 |

**推荐方向 A**，理由：用户是长时间盯屏的开发者，需要**高信息密度 + 强层级**；工具调用、路径、token 数字属于"技术数据"，用等宽字体与紧凑组件表达更专业；深色优先契合长时间使用。**建议保留一个品牌强调色**（见下）避免完全去个性化。**明确避免**：大渐变、卡通图标、过度圆角与彩色气泡等"消费级聊天 App"观感。

### 4. 品牌上下文（Brand Context）
现有品牌元素与处置建议：

| 元素 | 现状 | 建议 |

### 5. 规模（Scale）
- **窗口**：单窗口多面板；侧栏可折叠（`.collapsed`）、设置面板可展开（`.show`），无独立路由/多页。
- **改造范围**：侧栏（品牌区/按钮/工作区卡片/权限/会话列表/token 统计）＋ 主区（头部/设置面板/消息流/输入区）＋ 消息渲染（Markdown/代码/工具卡片/成本信息）。
- **必须完整保留**（硬约束，逐条见契约简报）：
  - **40 个 DOM id**（契约简报 §3，含 `ctxMenu` 动态创建、`emptyState` 内部结构不可变）。
  - **43 个后端方法调用**（§2），禁止改方法名 / 参数个数与顺序 / 返回值解析。
  - **全部内联 `onclick` 与函数签名**（§4），含 `imgInput/vidInput/fileInput/zipInput` 的 `.click()`。
  - **全部 JS 动态使用的 CSS 类名**（§5）。
  - **两套主题变量**（§6）：`body.dark` 必须同样成立，已有变量名不得删除（JS 内联引用 `var(--primary)` / `var(--chip-bg)` / `var(--err)`）。
- **响应式**：仅需适配桌面窗口尺寸（含窗口缩窄时侧栏折叠），无移动端断点要求。

## 二、本次重设计的成功标准（可验收）
1. **联通零回归**：43 个后端方法全部可调用成功，40 个 DOM id 全部存在，所有 `onclick` 触发正常——构建后 `glm-chat.html` 可正常收发消息、切换会话、读写工作区。
2. **工具调用可视化达标**：执行中 / 成功 / 失败三态清晰可辨，用户能一眼看出"AI 在做什么"。
3. **成本与权限显性化**：token/预算/权限档位在界面中随时可见，无需展开设置。
4. **双主题成立且护眼**：`light` / `dark` 两套均通过对比度检查，长时间使用无眩光。
5. **视觉一致性**：五大学派中选定方向贯穿全局，组件（按钮/卡片/下拉/徽章）风格统一，无"拼接感"。

## 三、必须守住的红线（引用契约简报）
1. **§1 铁律**：**永不直接改根目录 `glm-chat.html`**（构建产物）；只改 `frontend/` 源码并 `node frontend/build.js` 重新构建。
2. **§2 调用契约**：不得改后端方法名、参数个数/顺序、返回值解析方式。
3. **§3 DOM 契约**：40 个 id 一个都不能丢；`emptyState` 动态重建的内部 HTML 结构必须保持一致。
4. **§4 事件契约**：所有内联 `onclick` 处理函数必须存在且签名不变。
5. **§5 CSS 类契约**：JS 动态创建元素所用的全部类名必须保留并有效样式化。
6. **§6 主题契约**：`body.dark` 两套主题均须成立；已有 CSS 变量名不得删除。
7. **§7 联通缺口**：本轮**必须修复** `libs/` 引用错误——`marked.min.js→marked.js`、`purify.min.js→purify.js`、补齐 highlight 库，否则 Markdown 与代码高亮不生效。

## 四、交接给下游（Phase 2/3）
- 建议设计系统类型：**专业开发工具 / 技术极简**（方向 A）。
- 建议原型模板：**SaaS 桌面应用 / Dashboard 混合型**（单窗口多面板，非营销落地页）。
- 特别注意事项：工具调用卡片 + 成本仪表盘是本产品的**灵魂组件**，优先级高于常规聊天气泡；务必在 Phase 2 令牌中预留等宽字体族与状态色（ok/warn/err）。
